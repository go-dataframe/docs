Performance

go-dataframe against pandas 3.0 and polars, in time and memory: where it is faster, where polars is, and how it was measured.

You are reading the documentation of an outdated version, whose text may no longer be accurate. Go to the latest version.

All numbers are wall-clock medians of interleaved runs (Go, then pandas and polars, repeated), on an Apple M4 Max (16 cores, 128 GB), macOS, Go 1.27.2, pandas 3.0.6, polars (latest from PyPI via uv), numpy 2.5. The host is shared and was loaded by other work throughout (uptime load averages are given for each run); treat differences under ~1.5x as noise, and the polars column especially, since polars is multi-threaded too and suffers most from a busy machine.

Operations on a table

The table is built identically, value for value, by bench_test.go and bench/bench_pandas.py: key int64 in [0, 1000), x and y float64 in [0, 1), cat a string among 100 values. Operations:

  • groupby_sum: df.groupby("key").sum() — GroupBy("key").Sum()
  • groupby_sum_string: the same, keyed by the string column
  • sort_values: stable sort by x (pandas kind="stable", polars maintain_order=True)
  • filter: df[df.x > 0.5]
  • merge: inner join with a 1000-row table on key (unique on the right)
  • memory: bytes the table holds (Go: heap growth when building it; pandas: memory_usage(deep=True); polars: estimated_size())

Reproduce: sh bench/run.sh 1000000 5 > out.txt && python3 bench/medians.py out.txt.

Reading these honestly

  • Against pandas: sorting is about 2x faster (stable LSD radix sort), merge 1.3–1.7x, group-by on an int key at parity to 2x, group-by on a string key and the filter at parity or better. Nothing measured is slower than pandas by more than noise, except the string group-by in run A at 10^7, before factorisation went parallel.
  • Against polars: polars is faster on most operations on a quiet machine (2–4x on filter, merge and string group-by); sorting is close.
  • Memory is the weak point. Numeric columns cost what pandas’ cost (8 bytes a value). A string column is a Go []string: 16 bytes of header per value, plus the bytes (shared here, since there are only 100 distinct values). pandas 3 and polars store strings Arrow-style (offsets + one byte buffer), about 11 bytes a value here — so this table is 40 MB here against 35 MB in pandas and 27 MB in polars. Converting such a column to Category (4 bytes a value) makes it the smallest of the three. An Arrow-style string column is the obvious next step.
  • The merge benchmark joins on keys unique on the right with every left row matched, so the left columns are shared rather than gathered (columns are immutable); a join that duplicates or drops left rows gathers them.
  • Go’s garbage collector scans []string columns; with large string columns a share of the time in allocation-heavy operations (filter, merge) is GC.

CSV reader performance

Measured 2026-10-10 with bench/csv/bench.py (reproduce with the command in its docstring; the data files go to a temporary directory outside the repository).

Conditions

  • Apple M4 Max, 16 cores, 128 GB, macOS 26.6.2; Go 1.27.2; pandas 3.0.6, polars 2.0.0, pyarrow (pandas’ engine="pyarrow"), Python 3.12.12.
  • The machine was shared and loaded: load average 14–16 for most runs, rising to 45 during the last (10^7 rows, dates) series. Every reader ran under the same load, but absolute times are pessimistic and the spread is wide; the ratios are the meaningful part.
  • Table: id (int64), x (standard normal, full 17-digit precision), y (two decimals), cat (cat0..cat49), date (YYYY-MM-DD), as written by pandas’ to_csv. 10^6 rows = 49 MB, 10^7 rows = 497 MB.
  • Method: each read in its own process under /usr/bin/time -l; each process times only the read call (warm page cache, no process start-up). The readers run interleaved (ours, pandas C, pandas pyarrow, polars, ours, …), 5 rounds; the table gives the median (min–max).
  • “Data MB”: Go heap live after the read and a GC (runtime.MemStats. HeapAlloc), pandas memory_usage(deep=True).sum(), polars estimated_size(). These are not quite the same measure: ours includes the input buffer the string columns point into (see the memory trade-off in docs/design.md (CSV section)).
  • “Peak RSS”: maximum resident set size of the whole process. The Python processes include ~118 MB for the interpreter and the imports alone.

Reading

  • Against pandas’ default C parser: about 10× faster (9.9× at 10^6, 10.4× at 10^7), and 10–16× with dates parsed.
  • Against polars: within 5% at 10^6 and about 13% slower at 10^7 on the default read; level (within noise) with dates. Faster than pandas' pyarrow engine on every run but one.
  • Memory: the peak resident size of a read is in line with pandas and polars (lower once their interpreter baseline is counted), but the frame read holds about 2× pandas’ and 2.8× polars’ bytes, because the strings share the input buffer and Go strings carry 16-byte headers. That is the price of zero-copy strings; see docs/design.md (CSV section).

Go benchmarks (go test -bench 'ReadCSV|WriteCSV', in-memory, same table shape, load ~35): ReadCSV 10^6 rows ≈ 40–48 ms (≈1.1–1.3 GB/s); WriteCSV 10^5 rows ≈ 14 ms (≈400 MB/s).

Where the time goes (profile, 10^7 rows)

About half the CPU is the first conversion pass (integer and float parsing; strconv.ParseFloat for 17-digit values), a fifth the tokenizer, an eighth building the string columns, and a tenth the garbage collector marking the string columns. The remaining gap to polars is mostly float parsing (an Eisel–Lemire parser of our own would skip ParseFloat’s re-scan) and GC work on string headers.

Arrow and Parquet: performance

All measurements write and read a 10^6-row frame in memory, comparing arrowio (IPC) and parquetio (Parquet) with pandas (pyarrow engine). They were taken on 2026-10-10.

Setup

Frame. Six columns, built identically on both sides (benchFrame in arrowio/bench_test.go, for IPC, and in parquetio/bench_test.go, for Parquet; arrowio/testdata/bench_pandas.py on the pandas side):

columntypemissing
float64float641% NaN
int64int64none
string1,000 distinct values1%
category10 levelsnone
boolboolnone
datetimedatetimenone

Operations.

  • Parquet with Snappy compression, the default on both sides. parquetio produces a 15.2 MB file.
  • The Arrow IPC file format without compression. For pandas this is to_feather(compression="uncompressed").

Method.

  • 7 runs, with Go and pandas interleaved: a Go run, then a pandas run, and so on.
  • Each run reports the mean of 3 repetitions of each operation, in milliseconds.
  • The table gives the median of the 7 runs.

Machine. Apple M4 Max, 16 cores. The host is shared and was loaded throughout: uptime load averages were 14.97 / 18.50 / 18.88 before the runs and 14.15 / 17.96 / 18.67 after.

Versions. Go 1.27.2, apache/arrow-go v18.8.0. pandas 3.0.6, pyarrow 26.0.0, Python 3.12.12.

Where the time goes

Parquet write. About 70% of the allocations happen in arrow-go’s dictionary encoder for byte arrays: hashing.(*BinaryMemoTable).InsertOrGet makes about one allocation per string value (1.0 M allocations per write of the 10^6-row frame). pyarrow uses the same encoding, with dictionaries on by default, but in C++. Our conversion itself shares the numeric buffers and adds one pass for strings.

Parquet read. The time is dominated by arrow-go’s column decoding, which runs in parallel across columns. Our conversion is a minority of the profile:

  • copying the validity bitmaps (with bitutil.CopyBitmap)
  • one copy of each numeric buffer into the frame’s own array
  • one string allocation per chunk for the text

IPC read. pyarrow’s to_pandas is mostly zero-copy for numeric columns, so pandas pays almost nothing to read them. We copy every column once into storage the frame owns, because go-ndarray cannot adopt foreign memory. The string column also gets its []string headers built, and then copied once more by the core’s constructor.

IPC write. This is zero-copy for numeric and datetime columns, which is why it beats pandas.

How to rerun 

go test -c -o /tmp/arrowio.test ./arrowio
go test -c -o /tmp/parquetio.test ./parquetio
for i in 1 2 3 4 5 6 7; do
  /tmp/parquetio.test -test.run '^$' -test.bench . -test.benchtime 3x
  /tmp/arrowio.test -test.run '^$' -test.bench . -test.benchtime 3x
  (cd arrowio/testdata &&
    uv run --with pandas --with numpy --with pyarrow python bench_pandas.py)
done

The figures above were taken before Parquet moved to parquetio. The Parquet code itself did not change in the split, only its package.
